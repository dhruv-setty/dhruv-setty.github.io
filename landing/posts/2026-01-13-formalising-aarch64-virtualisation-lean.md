## The question

In a hypervisor, the property that has to remain true when nobody is observing is simple to state: a guest reaches only the memory it has been given, and once the hypervisor takes a page back, no core can reach it again. On Arm that property lives in two places, the Stage 2 translation tables that EL2 writes, and the TLB entries that cache them.

IATO v7 is the Arm virtualisation component of the IATO series. It defines, verifies and implements Stage 2 translation and TLB maintenance for a hypervisor at EL2. Its first version (v0.1.0) was a Lean 4 review of the specification against DDI 0487K, DDI 0608A, KVM and QEMU, preserved at the tag `archive/lean-v0.1.0`. Version v0.2.0, which this post walks through, replaces review with artefacts that run:

| Part | Artefact | Checked by |
|---|---|---|
| Normative reference | `spec/sail/stage2.sail`, `spec/sail/tlbi_scope.sail`, compiled to C | 8 Sail assertions, an independent Python walker |
| Stage 2 walker | `rtl/s2_walker.sv` | Sail reference and Python walker, Verilator cross check, Yosys |
| Stage 2 TLB | `rtl/s2_tlb.sv` | Icarus testbench with 13 checks, Sail TLBI scope assertions, Yosys |
| Unmap ordering | `spec/tla/S2Unmap.tla`, three configurations | TLC |

The scope is narrow on purpose: a 4 KiB granule, a 48 bit IPA and start level 0; Stage 2 only and combined TLB entries tagged by VMID and ASID; the operations TLBI IPAS2E1IS, VMALLE1IS, VMALLS12E1IS and VAE1IS; and the unmap of one IPA page across two cores. It is not a complete hypervisor or MMU. All results come from simulation and open tool synthesis, with no physical FPGA or silicon measurement. Every figure below was generated by the repository's captures workflow on an `ubuntu-24.04` runner; schematics are drawn by Yosys and netlistsvg, and every other figure is a screenshot of the named tool running.

## The reference comes first

<figure class="cs-figure"><img src="/journal/formalising-aarch64-virtualisation-lean/terminal_sail.png" alt="Terminal showing Sail 0.20.3 passing the TLBI scope assertions and the Stage 2 walk over five seeds with zero mismatches" width="780" height="375" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 1 · Sail checks</span> Sail 0.20.3: <code class="ic">build/sail_checks</code> passes the 8 TLBI scope assertions of <code class="ic">spec/sail/checks.sail</code>, and <code class="ic">build/s2_ref</code> runs the Sail Stage 2 walk over 2,000 probes for each of seeds 1 to 5 with 0 mismatches against the Python walker.</figcaption></figure>

The Sail model is the normative reference: every walker check is a comparison against it. Comparing it first against an independent Python walker matters, because a reference that agrees only with itself proves nothing. The probe generator builds random tables with pages, 2 MiB and 1 GiB blocks, invalid and reserved descriptors, the access flag clear, and every S2AP value, then probes inside and outside each mapping. The log shows the mix for seed 1: 505 successful translations, 1,074 translation faults, 347 permission faults and 74 access flag faults. Faults dominate, which is what a conformance test should exercise.

## The walker as built

<figure class="cs-figure"><img src="/journal/formalising-aarch64-virtualisation-lean/schematic_s2_walker.png" alt="Yosys and netlistsvg schematic of the s2_walker module" width="3222" height="2396" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 2 · s2_walker schematic</span> Stage 2 walker, 45 cells. Seven registers hold the walk state, level, table base, IPA, access type, response and response valid; multiplexers select the nine IPA index bits for each level and the output address for level 1, 2 and 3 leaves; comparators on the descriptor bits drive the translation, access flag and permission fault responses.</figcaption></figure>

The netlist is taken after Yosys `proc`, `opt -full` and `clean`, before technology mapping, so the cells are RTL operators and registers. That makes the schematic readable against the requirements. S2-W-01 (resolve a 48 bit IPA in at most four levels, nine IPA bits per level) is the index multiplexer. S2-W-02 to S2-W-05 (translation, reserved descriptor, access flag and permission faults) are the descriptor comparators. S2-W-06 fixes the result word: bit 63 fault, bits 62 to 60 kind, bits 59 to 58 level, bits 47 to 0 output address, the same encoding as Sail. The walker never updates the access flag; hardware access flag and dirty state update (FEAT_HAFDBS) is out of scope.

## The walker against the reference

<figure class="cs-figure"><img src="/journal/formalising-aarch64-virtualisation-lean/testbench_2-tb_s2_walker.png" alt="Geany with tb_s2_walker.cpp open and the simulation log below" width="1600" height="1050" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 3 · Walker harness</span> <code class="ic">tb_s2_walker.cpp</code>: the Verilator harness that drives <code class="ic">s2_walker</code> with the generated probes, models table memory with a configurable latency and compares every response with the expected word. The log below shows 0 mismatches at memory latencies 1, 8 and 32.</figcaption></figure>

The harness is a three way agreement: the Sail reference, the Python walker and the RTL must agree on every probe. Across the release checks that is 10,000 random probes over five table sets with 0 mismatches. A test that cannot fail is not evidence, so the repository also plants a permission fault in the RTL: it produces 330 mismatches in 2,000 probes. The log in this figure also carries the latency result, since the walker holds one table read in flight and a full walk costs `1 + 4 × (latency + 1)` cycles:

| Memory latency (cycles) | Mean cycles per walk, all probes | Four level walk |
|---|---|---|
| 1 | 6.22 | 9 cycles |
| 8 | 24.49 | 37 cycles |
| 32 | 87.11 | 133 cycles |

The mean is lower than the four level figure because most faulting probes terminate at an early level.

## The walk in a waveform

<figure class="cs-figure"><img src="/journal/formalising-aarch64-virtualisation-lean/waveform_s2_walker_lat1.png" alt="GTKWave view of s2_walker at memory latency 1" width="1600" height="440" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 4 · s2_walker, latency 1</span> <code class="ic">s2_walker</code> at memory latency 1, first 120 cycles of the seed 1 probes: each request raises <code class="ic">mem_req</code> once per level, <code class="ic">level</code> advances from 0 towards 3, and <code class="ic">resp_valid</code> pulses for one cycle with the output address or fault word in <code class="ic">resp</code>.</figcaption></figure>

The waveform is recorded from a copy of the Verilator harness with identical stimulus and checks, built with `--trace`; the RTL is unchanged and the traced run reports the same `PASS`. At latency 1 the structure of the walk is visible as one table read per level and a single cycle response.

<figure class="cs-figure"><img src="/journal/formalising-aarch64-virtualisation-lean/waveform_s2_walker_lat8.png" alt="GTKWave view of s2_walker at memory latency 8" width="1600" height="440" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 5 · s2_walker, latency 8</span> At memory latency 8 each table read waits for <code class="ic">mem_rvalid</code>. The three probes shown each end at level 2: a 2 MiB block translation (<code class="ic">0000FDA91E306C60</code>), a permission fault (<code class="ic">B800000000000000</code>) and a translation fault (<code class="ic">9800000000000000</code>), in the result encoding of S2-W-06.</figcaption></figure>

This figure is the encoding requirement made visible. The two fault words decode by the S2-W-06 layout: bit 63 set for a fault, the kind in bits 62 to 60, and level 2 in bits 59 to 58. The same three probes also show where the time goes: each level is one serialised memory read, which is why the planned work is to overlap walks and cache level 0 to 2 descriptors before measuring again at latency 32.

## The TLB as built

<figure class="cs-figure"><img src="/journal/formalising-aarch64-virtualisation-lean/schematic_s2_tlb_n2.png" alt="Yosys and netlistsvg schematic of s2_tlb with two entries" width="3208" height="3296" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 6 · s2_tlb schematic, N = 2</span> Stage 2 TLB with <code class="ic">N = 2</code>, 82 cells: per entry valid, combined, global, VMID, ASID, page and PA registers; the VMID, page and ASID comparators that drive <code class="ic">lk_hit</code> and select <code class="ic">lk_pa</code>; the TLBI kill logic decoded from <code class="ic">tlbi_op</code>; and the round robin fill pointer.</figcaption></figure>

The parameter `N` is set to 2 with `chparam` so the per entry structure is legible; the default eight entry TLB has 263 cells. The schematic shows the lookup rule directly: lookups match on VMID, and combined lookups also match on ASID unless the entry is global. The kill logic is where the TLBI scope requirements live.

## The TLB against its scopes

<figure class="cs-figure"><img src="/journal/formalising-aarch64-virtualisation-lean/testbench_1-tb_s2_tlb.png" alt="Geany with tb_s2_tlb.sv open and the simulation log below" width="1600" height="1050" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 7 · TLB testbench</span> <code class="ic">tb_s2_tlb.sv</code>: TLB fills tagged by VMID and ASID, lookups, and the four TLBI scopes, with the run log below. Icarus Verilog 12.0 compiles and runs it and prints <code class="ic">PASS</code>.</figcaption></figure>

The testbench has 13 directed checks against the scope table:

| ID | Operation | The TLB removes |
|---|---|---|
| S2-T-01 | IPAS2E1IS | Stage 2 only entries of the VMID for the IPA page |
| S2-T-02 | VMALLE1IS | Combined entries of the VMID |
| S2-T-03 | VMALLS12E1IS | All entries of the VMID |
| S2-T-04 | VAE1IS | Combined entries of the VMID for the VA page, with a matching ASID or the global attribute |
| S2-T-05 | Any operation | No entry of any other VMID |

The `sorry: Case unique/unique0 qualities are ignored` line in the log is an Icarus warning on `rtl/s2_tlb.sv`. Verilator lints the same file clean (Figure 12).

<figure class="cs-figure"><img src="/journal/formalising-aarch64-virtualisation-lean/waveform_tb_s2_tlb.png" alt="GTKWave view of the tb_s2_tlb simulation" width="1600" height="608" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 8 · tb_s2_tlb waveform</span> Four fills (a Stage 2 entry of VMID 1, a combined entry of VMID 1 and ASID 5, a global combined entry, and a combined entry of VMID 2) set <code class="ic">v</code> to <code class="ic">0F</code>; lookups follow, then TLBI operations 0 to 3 (IPAS2E1IS, VMALLE1IS, VMALLS12E1IS, VAE1IS), each of which asserts <code class="ic">kill</code> for the entries in its scope. The testbench refills between scopes. <code class="ic">errors</code> remains 0.</figcaption></figure>

The four fills are chosen so that each scope has something to remove and something it must leave: a different VMID, a different entry type, and a global entry. The `kill` pattern per operation is the scope table above, observed in hardware rather than asserted in prose. The detail that matters for the next section is S2-T-01: IPAS2E1IS removes Stage 2 only entries and leaves combined entries alone.

## Ordering is a correctness requirement

The unmap requirement is S2-U-01: clear the descriptor, DSB, TLBI IPAS2E1IS, DSB, TLBI VMALLE1IS, DSB, and only then free the frame. The TLA+ model has two cores; each can cache a Stage 2 entry (`S2`) and a combined entry (`CB`), and can refill a combined entry from a cached Stage 2 entry without reading the tables. Broadcast TLBIs complete at the next DSB. The safety property `NoUseAfterFree` states that no guest access reaches the frame after it is freed.

<figure class="cs-figure"><img src="/journal/formalising-aarch64-virtualisation-lean/terminal_tlc_S2Unmap.png" alt="Terminal showing TLC completing on S2Unmap.cfg with no error" width="1380" height="307" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 9 · TLC, required sequence</span> Required sequence (S2-U-01): model checking completes with no error; 435 states generated, 74 distinct states, depth 8.</figcaption></figure>

The required sequence holds over every reachable state of the model. That is a statement about this model, one IPA page and two cores, and nothing larger: the model does not cover memory ordering beyond DSB completion.

<figure class="cs-figure"><img src="/journal/formalising-aarch64-virtualisation-lean/terminal_tlc_S2Unmap_no_vmalle1.png" alt="Terminal showing TLC finding a NoUseAfterFree violation when VMALLE1IS is omitted" width="1380" height="953" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 10 · TLC, VMALLE1IS omitted</span> S2-U-02: <code class="ic">NoUseAfterFree</code> is violated in an 8 state counterexample. After the hypervisor clears the descriptor, and before the DSB makes it visible to the walkers, core <code class="ic">c1</code> fills a combined entry; IPAS2E1IS completes at the next DSB without removing it, the frame is freed, and <code class="ic">Access(c1)</code> reaches the frame through the surviving combined entry.</figcaption></figure>

<figure class="cs-figure"><img src="/journal/formalising-aarch64-virtualisation-lean/terminal_tlc_S2Unmap_vmalle1_first.png" alt="Terminal showing TLC finding a NoUseAfterFree violation when VMALLE1IS is issued first" width="1380" height="1157" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 11 · TLC, VMALLE1IS first</span> S2-U-03: <code class="ic">NoUseAfterFree</code> is violated in an 11 state counterexample. Core <code class="ic">c1</code> caches a Stage 2 entry before the cleared descriptor becomes visible; after VMALLE1IS completes and while IPAS2E1IS is pending, <code class="ic">FillCB(c1)</code> refills a combined entry from the cached Stage 2 entry, IPAS2E1IS then removes only the Stage 2 entry, and the access after the free uses the combined entry.</figcaption></figure>

The two counterexamples are the most useful figures in the repository, because each one is a short, concrete trace of a plausible hypervisor bug:

| Configuration | Sequence | Result |
|---|---|---|
| `S2Unmap` | clear, DSB, IPAS2E1IS, DSB, VMALLE1IS, DSB, free | Holds, 74 distinct states |
| `S2Unmap_no_vmalle1` | clear, DSB, IPAS2E1IS, DSB, free | Violated: a combined entry survives the free |
| `S2Unmap_vmalle1_first` | clear, DSB, VMALLE1IS, DSB, IPAS2E1IS, DSB, free | Violated: a combined entry is refilled after VMALLE1IS |

Both broken sequences issue the right instructions in some form; one omits a step and the other swaps two. Instruction order is therefore a correctness requirement, not an optimisation, and `check.sh` fails if either incorrect ordering stops violating the property.

## Lint and synthesis, with the versions stated

<figure class="cs-figure"><img src="/journal/formalising-aarch64-virtualisation-lean/terminal_lint_synth.png" alt="Terminal showing Verilator lint passing on both modules and Yosys and nextpnr synthesis results" width="628" height="324" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 12 · Lint and ECP5 synthesis</span> Verilator 5.020 lints both modules clean. <code class="ic">bench/synth.sh</code> with Yosys 0.33 and nextpnr-ecp5 0.6 reports <code class="ic">s2_walker</code> at 296 LUT4, 143 FF and 213.95 MHz, and <code class="ic">s2_tlb</code> at 3,198 LUT4, 859 FF, 16 CCU2C and 92.58 MHz.</figcaption></figure>

These numbers do not match the committed synthesis table, and the README says so rather than hiding it. The committed figures are reproduced exactly by Yosys 0.52 with nextpnr-ecp5 0.7; the Ubuntu 24.04 packages in CI map and route the same RTL differently.

| Module | Yosys 0.52, nextpnr-ecp5 0.7 (committed) | Yosys 0.33, nextpnr-ecp5 0.6 (this figure) |
|---|---|---|
| `s2_walker` | 370 LUT4, 143 FF, 236.57 MHz | 296 LUT4, 143 FF, 213.95 MHz |
| `s2_tlb` (8 entries) | 3,246 LUT4, 859 FF, 136.72 MHz | 3,198 LUT4, 859 FF, 92.58 MHz |

Both are out of context estimates on a Lattice LFE5U-25F, not vendor tool or ASIC figures, and the walker and TLB are synthesised as separate blocks, so integrated timing has not been measured. The engineering point is the one the README draws: an open tool synthesis result is only meaningful with its tool versions attached.

## What remains to be shown

- A cross check of the walker and TLBI scopes against a QEMU TCG guest at EL2.
- Overlapped walks and cached level 0 to 2 descriptors, measured at latency 32.
- Concatenated start tables with a 40 bit IPA and start level 1, and FEAT_HAFDBS.
