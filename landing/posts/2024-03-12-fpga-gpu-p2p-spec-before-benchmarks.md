## Specification first

Moving data between accelerators looks simple until the path is examined. A device has to be found and given address space, every transaction header has to be decoded exactly, and a copy engine has to hand buffers back to software in an order that software can trust. A peer-to-peer data path to a GPU depends on all three, and none of them is a benchmark question. They are correctness questions, and they come first.

The IATO repository builds that device side of the path. It is not a production device, driver or IP core, and it does not implement a GPU or a peer-to-peer transfer. Its PCIe and DMA features are a Type 0 configuration space, a TLP header decoder, a descriptor ring DMA engine with a C driver, and a TLA+ model of PCIe posted-write ordering. All results come from model checking, simulation and open tool synthesis, with no physical FPGA and no vendor tools. Every figure below was generated by the repository's captures workflow on an `ubuntu-24.04` runner.

Two specifications are written before any RTL is measured:

| Specification | Statement | Result |
|---|---|---|
| `spec/pcie/TLPOrdering.tla` | A producer writes data, then a flag; a consumer reads the flag, then the data | Safe with strict posted ordering. Relaxed Ordering on the flag write lets the consumer read stale data |
| DMA descriptor handoff (Sail, in `spec/sail/`) | The driver writes source, destination and length, sets OWN last, issues a write barrier, then rings the TAIL doorbell. The engine writes back OWN cleared and DONE set, and only then advances HEAD and DONE_CNT in the same cycle | Part of the 14 Sail assertions, all passing |

The ordering result is the one a P2P design most needs to hear before it chooses a fast path: Relaxed Ordering on the flag write is not an optimisation that can be applied blindly, because it breaks the flag then data pattern.

## Enumeration: the configuration space

<figure class="cs-figure"><img src="/journal/fpga-gpu-p2p-spec-before-benchmarks/schematic_cfg_space.png" alt="Yosys and netlistsvg schematic of the cfg_space module" width="3200" height="2098" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 1 · cfg_space schematic</span> Type 0 configuration space. Register select comparators gate writes to the Command register and to BAR0, BAR2 and BAR3, whose low bits are masked to the BAR size; the read multiplexer returns the ID, class and BAR words.</figcaption></figure>

The netlist is taken after Yosys `proc`, `opt -full` and `clean`, before technology mapping, so each cell is an RTL operator or register. The BAR masking is the part to read. Software sizes a BAR by writing all ones and reading back which bits stuck; the low bits masked to the BAR size are what make that read back report the size. The header carries a 32 bit BAR0 and a 64 bit prefetchable BAR pair in BAR2 and BAR3.

<figure class="cs-figure"><img src="/journal/fpga-gpu-p2p-spec-before-benchmarks/testbench_3-tb_enum.png" alt="Geany with tb_enum.sv open and the Icarus simulation log below" width="1600" height="1000" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 2 · tb_enum testbench</span> <code class="ic">tb_enum.sv</code> open in the editor: bus 0 scan, BAR sizing, aligned assignment and enable, with the run log below. Icarus Verilog 12.0 prints <code class="ic">PASS tb_enum</code>.</figcaption></figure>

The log line for each device found is the enumeration result:

| Bus and device | Vendor | Device | BAR0 | BAR2 (64 bit, prefetchable) |
|---|---|---|---|---|
| bus 0, dev 1 | `abcd` | `0011` | 4 KiB at `c0000000` | 1024 KiB at `0000004000000000` |
| bus 0, dev 3 | `abcd` | `0033` | 64 KiB at `c0010000` | 16384 KiB at `0000004001000000` |

The testbench scans bus 0, skips empty slots, sizes every BAR by writing all ones, assigns naturally aligned addresses and enables Memory Space and Bus Master. The addresses in the log are naturally aligned to their sizes, and each 64 bit BAR2 is assigned above the 4 GiB boundary. The `sorry: constant selects` lines are Icarus warnings on `rtl/pcie/cfg_space.sv`; Verilator lints the same file clean.

The waveform shows the sizing protocol as it happens on the wire: `wd` carries `FFFFFFFF`, `cfg_rdata` returns the masked value, and the BAR base registers then take their assigned addresses. The testbenches set no `timescale`, so GTKWave labels simulator time steps as seconds.

## Transactions: the TLP header decoder

<figure class="cs-figure"><img src="/journal/fpga-gpu-p2p-spec-before-benchmarks/schematic_tlp_hdr_decode.png" alt="Yosys and netlistsvg schematic of the tlp_hdr_decode module" width="1600" height="2505" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 4 · tlp_hdr_decode schematic</span> PCIe TLP header decoder. The 128 bit header fans out to format and type decode, length, traffic class, attributes, requester ID, tag, byte enables and the 32 or 64 bit address; the design is purely combinational.</figcaption></figure>

A purely combinational decoder has no state to get wrong, which leaves one thing to verify: that every field is taken from the right bits of the 3DW or 4DW header. The attributes field is decoded with the rest, and the ordering result above depends on attributes such as Relaxed Ordering being read exactly.

Icarus Verilog 12.0 prints <code class="ic">PASS tb_tlp_hdr_decode</code>.</figcaption></figure>

<figure class="cs-figure"><img src="/journal/fpga-gpu-p2p-spec-before-benchmarks/waveform_tb_tlp_hdr_decode.png" alt="GTKWave view of tb_tlp_hdr_decode" width="1600" height="656" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 6 · tb_tlp_hdr_decode waveform</span> One header per step, with the decoded type flags, length, attributes, requester ID, tag and address; <code class="ic">be_malformed</code> rises for the illegal byte enable case. <code class="ic">errors</code> stays at 0.</figcaption></figure>

The malformed case is the one to look for in the trace. A decoder that only ever sees legal headers has not been tested for the input an untrusted peer can send. Here the illegal byte enable combination raises `be_malformed`, and `errors` stays at 0 across every step.

## Copies: the DMA engine and its driver

The engine walks a ring of 32 byte descriptors in host memory, copies 8 bytes per beat over one memory port shared between reads and writes, and keeps up to `MAX_RD` reads outstanding. The driver reaps by reading DONE from memory, so the fast path does not touch a register. An early version updated DONE_CNT one cycle after writing DONE, and the driver could read a stale count. The fix is in the RTL, and the harness now checks the count after every run.

<figure class="cs-figure"><img src="/journal/fpga-gpu-p2p-spec-before-benchmarks/waveform_dma_two_descriptors.png" alt="GTKWave view of the DMA engine processing two descriptors" width="1600" height="736" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 7 · dma_engine, two descriptors</span> <code class="ic">dma_engine</code> with the C driver under Verilator: register writes ring the doorbell to <code class="ic">tail = 2</code>, the engine fetches each descriptor, keeps up to four reads outstanding at latency 4, writes the data back, and advances <code class="ic">head</code> and <code class="ic">done_cnt</code>.</figcaption></figure>

This trace is the handoff specification observed in simulation. The register writes at the start ring the doorbell, and `tail` becomes `0002`. `outstanding` climbs to 4 while data is read, the four reads in flight that the README describes at latency 4. When the first descriptor completes, `head` and `done_cnt` change together, from `0000` to `0001` and from 0 to 1, which is exactly the property the early version violated. The time axis is harness ticks recorded in picoseconds.

<figure class="cs-figure"><img src="/journal/fpga-gpu-p2p-spec-before-benchmarks/bench-wave-dma_two_descriptors.png" alt="Logic analyser style plot of the DMA engine states, memory requests, outstanding reads and head over 70 cycles" width="2100" height="864" loading="lazy" decoding="async" /><figcaption><span class="cs-figure__label">Figure 8 · dma_engine, logic analyser view</span> The same VCD rendered by <code class="ic">bench/vcd_view.py</code>: two 64 byte descriptors at memory latency 4, plotted against cycles. The state machine runs IDLE, FETCH, FWAIT, COPY for each descriptor, and <code class="ic">head</code> advances from 0 to 1 and then to 2.</figcaption></figure>

Plotted in cycles, the cost structure is visible. Each descriptor spends cycles in FETCH and FWAIT before any payload moves, and the COPY phase interleaves read requests with write requests (`mem_req_we`) on the single port. For a 64 byte copy the fetch and writeback of the descriptor are a large share of the total, which is what the benchmark below measures.

## Only then, the benchmarks

With the handoff shown to be correct, the throughput numbers mean something. `bench/run.sh` sweeps copy size, memory latency and `MAX_RD`. The ceiling is 4 bytes per cycle, because the one port takes one request per cycle shared between reads and writes. Values are bytes per cycle, and every copy in the sweep is verified byte for byte.

| Copy size | Latency 1 | Latency 8 | Latency 32, MAX_RD 8 | Latency 32, MAX_RD 32 |
|---|---|---|---|---|
| 64 B | 2.46 | 1.88 | 0.78 | 0.78 |
| 512 B | 3.71 | 3.35 | 1.39 | 2.99 |
| 4 KiB | 3.96 | 3.71 | 1.54 | 3.79 |
| 64 KiB | 4.00 | 3.76 | 1.56 | 3.93 |

Three readings follow from the table, and each was predictable from the specification:

- At latency 32 with 8 reads in flight the engine is bound by Little's law: 8 beats of 8 bytes per round trip. With 32 in flight it reaches within 2 percent of the ceiling.
- Small copies are bound by the descriptor fetch and writeback seen in Figure 8, which is the case for batching or prefetching descriptors. Descriptor prefetch is planned work, not implemented.
- In the README's synthesis table, `dma_engine` with `MAX_RD` 8 places and routes at 129.10 MHz on a Lattice LFE5U-25F, out of context, so the ceiling of 4 bytes per cycle is about 516 MB/s. That is an open tool estimate, not a vendor tool, ASIC or FPGA measurement, and the Fmax with `MAX_RD` 32 has not been measured.

## What is still owed

The repository lists its planned PCIe and DMA work, none of it implemented: completion ordering and a TLP generator wired to the DMA engine; descriptor prefetch, scatter gather and MSI on completion; a Linux PCI driver skeleton using the same register map; and SystemVerilog assertions on the DMA handoff checked with SymbiYosys. A physical FPGA measurement and the GPU side of a peer-to-peer path are outside it entirely. What exists is the part that has to be right before any of that is worth timing.
